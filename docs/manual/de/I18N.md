# Sprachen (i18n)

> **Wo Sie sich im Handbuch befinden.** Dieses Kapitel
> behandelt die Sprachumschalt-Funktion, die für jeden
> Benutzer sichtbar ist (über das Benutzer-Dropdown), plus
> die technischen Details zum Hinzufügen / Aktualisieren
> von Übersetzungen für den technischen Leser.
>
> **Außerhalb des Bereichs.** Datums- und Zahlenformatierung
> sind an die Browser-Locale gebunden, nicht an die
> Spracheinstellung von RASTATIME. Die Sprache von
> RASTATIME beeinflusst nur UI-Labels.

RASTATIME wird mit **Englisch** und **Deutsch** ausgeliefert.
Französische und spanische Übersetzungen sind vorhanden,
aber teilweise (maschinell übersetzt, als fuzzy markiert).
Jedes Label, das Operatoren in der Web-Oberfläche sehen,
geht durch `gettext` und kann übersetzt werden.

Die Sprache kann gesetzt werden:

- **Systemweit** — Einstellungen → Allgemeine
  Einstellungen → Standardsprache. Der Anmeldebildschirm +
  neue Benutzer verwenden dies als Standard.
- **Per Benutzer** — Benutzer-Dropdown → **Sprache** →
  auswählen. Mit dem Benutzerkonto gespeichert; tritt bei
  der nächsten Anmeldung in Kraft.
- **Per Anfrage** — Nicht direkt unterstützt;
  URL-Parameter-Übersteuerung ist nicht implementiert.

## 1. Die eigene Sprache wechseln

Oben rechts Benutzer-Dropdown → **Sprache** → aus der
Liste auswählen.

```
   ┌──────────────────────┐
   │  ↓  admin            │
   ├──────────────────────┤
   │  Mein Profil         │
   │  Sprache ▾           │
   │    ◯  Englisch       │
   │    ◉  Deutsch        │
   │    ◯  Französisch    │
   │    ◯  Spanisch       │
   │  Abmelden            │
   └──────────────────────┘
```

Die Wahl wird mit Ihrem Benutzerkonto in `cc_subjs`
gespeichert. Melden Sie sich ab und wieder an (oder laden
Sie die Seite neu), damit die Änderung vollständig in Kraft
tritt — die Sprache wird einmal pro Session beim Anmelden
geladen.

> **Warum übersetzt die Seite teilweise?** PHP-Templates
> rendern zur Anfrage-Zeit, sodass sie sofort
> aktualisieren. Client-seitige JavaScript-Strings werden
> einmal beim Seitenladen geladen und brauchen einen
> vollständigen Page-Refresh, um zu aktualisieren. Vor
> 2026-05-15 behielten einige Menü-Labels sogar ihren
> vorherigen-Locale-Wert über fcgid-Worker-Recycling
> hinweg; das ist der Bug, den ARCHITECTURE §20.3 abdeckt
> + der Fix in Commit 3b4bcb6.

## 2. Die vier ausgelieferten Sprachen

| Locale | Status | Hinweise |
|---|---|---|
| **en_US** | Quellsprache, 100 % | Die Referenz. Alle msgid-Schlüssel sind en_US. |
| **de_DE** | Vollständig, operator-überprüft | Die primäre deutsche Locale des RASTATIME-Teams. |
| **fr_FR** | Teilweise, maschinell übersetzt | Auto-übersetzt aus en_US; fuzzy-Marker auf unsicheren Strings. Community-Beiträge willkommen. |
| **es_ES** | Teilweise, maschinell übersetzt | Dasselbe wie fr_FR. |

Nicht-englische / nicht-deutsche ursprüngliche
LibreTime-Locales wurden in Commit 1724246 entfernt, um den
Übersetzungsaufwand auf die zwei operator-unterstützten
Sprachen zu fokussieren.

## 3. Wie Übersetzungen technisch funktionieren

> **Für den technischen Leser.** Operatoren können diesen
> Abschnitt überspringen.

### gettext unter Windows ohne msgfmt

RASTATIME läuft unter Windows, wo die GNU-gettext-Toolchain
(`msgfmt`) umständlich zu installieren ist. Um Operatoren
nicht zur Installation zu zwingen, liefert RASTATIME einen
**reinen Python-.po-→-.mo-Compiler** unter
`scripts/compile_messages.py`. Die kompilierten
.mo-Dateien sind auch im Repository committed, sodass ein
frischer Clone ohne Ausführung des Compilers funktioniert.

Zum Neuaufbau der .mo-Dateien nach Bearbeitung einer .po:

```powershell
python scripts/compile_messages.py
```

Oder verwenden Sie den Convenience-Wrapper:

```powershell
infra/scripts/maintenance/build-locales.ps1
```

### Wo die Dateien leben

```
   frontend/legacy/locale/
     en_US/LC_MESSAGES/
       rastatime.po      ← Englische Quelle (msgid + identische msgstr)
       rastatime.mo      ← kompiliert
     de_DE/LC_MESSAGES/
       rastatime.po      ← Deutsche Übersetzungen
       rastatime.mo      ← kompiliert
     fr_FR/LC_MESSAGES/
       rastatime.po      ← Französisch (teilweise)
       rastatime.mo      ← kompiliert
     es_ES/LC_MESSAGES/
       rastatime.po
       rastatime.mo
   backend/api/locale/
     de/LC_MESSAGES/
       django.po         ← Django-API-Fehlermeldungen (Deutsch)
       django.mo
   frontend/locales/
     en/common.json      ← JSON-Form für JS-i18n
     de/common.json
```

Drei Formate:

- **`rastatime.po/.mo`** — gettext-Format, vom PHP über die
  Funktionen `_()` und `gettext()` auf dem Legacy-Frontend
  verwendet.
- **`django.po/.mo`** — gettext-Format, von Django für
  REST-API-Fehlermeldungen verwendet.
- **`common.json`** — JSON-Form, von JavaScript über
  `$.i18n._()` für client-seitig gerenderte Strings
  verwendet.

### Einen neuen übersetzbaren String hinzufügen

PHP (am häufigsten):

```php
// Vorher
$label = 'Save Changes';

// Nachher
$label = _('Save Changes');
```

JavaScript:

```js
// Vorher
var label = 'Save Changes';

// Nachher
var label = $.i18n._('Save Changes');
```

Dann den String in die `.po`-Dateien extrahieren:

```powershell
# Aus dem Repo-Root
xgettext --keyword=_ --output=frontend/legacy/locale/en_US/LC_MESSAGES/rastatime.po \
   $(Get-ChildItem frontend/legacy/application -Recurse -Filter *.php)
```

> **Tipp.** RASTATIME führt `xgettext` derzeit nicht bei
> jedem Commit aus. Vorerst fügen Sie neue Strings per
> Hand in die `.po`-Dateien ein oder batch-extrahieren vor
> einem Release.

### Das Render-Time-Übersetzungs-Muster (T20.3)

Einige Labels — insbesondere das Top-Navigations-Menü —
wurden früher zur *Config-Load*-Zeit in
`configs/navigation.php` übersetzt. Das bedeutete, dass
der fcgid-Worker den vorher gerenderten String hielt, und
ein Sprachwechsel propagierte nicht, bis der Worker
recycled wurde. RASTATIME 2026-05-15 (Commit 3b4bcb6)
verschob die Menü-Übersetzung auf *Render*-Zeit in
`views/scripts/menu.phtml`:

```phtml
<?php // navigation.php — Labels sind reine englische Quellstrings ?>
<?php // menu.phtml — übersetzt tatsächlich zur Render-Zeit ?>
<a href="…"><?php echo _($page->getLabel()); ?></a>
```

Implikation für Übersetzer: Wenn Sie Strings aus dem
Navigationsmenü extrahieren, ist die Quelle, die Sie in
`configs/navigation.php` sehen, die **msgid**, nicht das
Anzeige-Label.

## 4. Eine neue Locale hinzufügen

> **Für den technischen Leser.** Operatoren können diesen
> Abschnitt überspringen.

Hinzufügen von (z.B.) Italienisch:

1. **Locale-Code wählen.** `it_IT` ist kanonisch.
2. **Verzeichnisse erstellen:**

```powershell
mkdir frontend/legacy/locale/it_IT/LC_MESSAGES
mkdir backend/api/locale/it/LC_MESSAGES
mkdir frontend/locales/it
```

3. **`en_US/LC_MESSAGES/rastatime.po` als Ausgangspunkt
   kopieren:**

```powershell
copy frontend/legacy/locale/en_US/LC_MESSAGES/rastatime.po `
     frontend/legacy/locale/it_IT/LC_MESSAGES/rastatime.po
```

4. **msgstr-Felder übersetzen** in der neuen .po-Datei.
   In Poedit (Linux/Mac) oder PoEditor (Web) für eine
   freundlichere UI öffnen. Unsichere Übersetzungen als
   `#, fuzzy` markieren.

5. **Kompilieren:**

```powershell
python scripts/compile_messages.py
```

6. **Die Locale zu `application/models/Locale.php`s
   `getLocales()` hinzufügen**, damit sie im Dropdown
   erscheint:

```php
'it_IT' => 'Italiano',
```

7. **Optional: `backend/api/locale/`s `django.po`** für
   italienische API-Fehlermeldungen übersetzen.

8. **Optional: `frontend/locales/it/common.json`** für
   client-seitige JS-Strings übersetzen.

9. **Testen:** anmelden, Sprache wechseln, jede Seite
   durchgehen. Suchen Sie nach englischen Strings, die
   nicht übersetzt wurden — das sind fehlende
   `_()`-Wrapper in der PHP-Quelle (Bug einreichen).

## 5. Bestehende Übersetzungen bearbeiten

Der einfachste Pfad:

```powershell
# In einem beliebigen Texteditor öffnen
notepad frontend/legacy/locale/de_DE/LC_MESSAGES/rastatime.po
```

Suchen Sie die msgid, die Sie beheben möchten, ändern Sie
ihre msgstr, speichern Sie. Neu kompilieren:

```powershell
python scripts/compile_messages.py
```

Browser-Refresh → aktualisierte Übersetzung sichtbar.

### PO-Datei-Format-Primer

```
msgid "Save Changes"
msgstr "Änderungen speichern"

msgid "Cancel"
msgstr "Abbrechen"

#, fuzzy
msgid "Sometimes uncertain string"
msgstr "Manchmal unsicherer String"
```

- `msgid` — der englische Quellstring (unveränderlich).
- `msgstr` — der übersetzte String. Bearbeiten Sie dies.
- `#, fuzzy` — Kommentar, der die Übersetzung als unsicher
  markiert. Entfernen Sie die Kommentarzeile, sobald Sie
  überprüft haben.

### Pluralformen

```
msgid "1 track"
msgid_plural "%d tracks"
msgstr[0] "1 Track"
msgstr[1] "%d Tracks"
```

Deutsch hat dieselbe Singular/Plural-Unterscheidung wie
Englisch. Andere Sprachen können mehr haben (z.B. hat
Russisch 3 Formen). Siehe gettext-Dokumentation für die
per-language `nplurals`-Zahl.

## 6. Datums- und Zahlenformatierung

Diese werden **nicht** von der RASTATIME-Spracheinstellung
gesteuert. Sie folgen der **Browser-Locale**
(`navigator.language` in JS) für client-seitiges Rendern
und der **Operator-Zeitzone** (Einstellungen → Allgemeine
Einstellungen → Zeitzone) für server-seitiges Rendern.

Um deutsches Datumsformat zu erhalten ("21.05.2026" statt
"05/21/2026"):

- Setzen Sie Ihre Browser-Sprache auf de-DE (in Ihren
  OS-Einstellungen).
- RASTATIME-UI-Strings können auf Englisch bleiben; nur
  Daten ändern sich.

Server-seitige Datumsformatierung verwendet die PHP-Locale,
die im `Locale.php`-Modell gesetzt ist, das den Sprachcode
spiegelt.

> **Warum auf diese Weise getrennt?** Ein Benutzer, der in
> englischem Text arbeitet, aber ISO-Datumsformat
> ("2026-05-21") bevorzugt, sollte nicht die gesamte UI
> auf Deutsch umstellen müssen, nur für das Datum. Die
> beiden sind absichtlich entkoppelt.

## 7. Häufig gestellte Fragen

### "Ich habe die Sprache geändert, aber einige Strings sind noch Englisch."

Ursachen:

- Der String in der PHP-Quelle ist nicht in `_()`
  gewrappt. Bug einreichen.
- Die `.po`-Datei hat die msgstr für diese msgid leer (sie
  fällt auf die msgid zurück). .po bearbeiten, Übersetzung
  hinzufügen, neu kompilieren.
- Ihr Browser hat die JS-Strings gecached. Hard-Refresh
  (Strg+Umschalt+R).

### "Die 'admin'-Anmeldeseite ist in der falschen Sprache."

Die Anmeldeseite verwendet die **System-Standardsprache**
(Allgemeine Einstellungen → Standardsprache), weil noch
keine Benutzersession existiert. Setzen Sie den
System-Standard auf Ihre bevorzugte Sprache.

### "Kann ich Sendungen in einer Sprache und die UI in einer anderen haben?"

Ja. Sendungsnamen, Beschreibungen, Hostnamen sind
beliebige Benutzereingaben — sie erscheinen genau wie
eingegeben, unabhängig von der UI-Sprache. Nur die eigenen
UI-Labels von RASTATIME werden übersetzt.

### "Warum antwortet die Django-API auf Englisch, wenn meine UI Deutsch ist?"

Die Django-API hat ihren eigenen Übersetzungssatz
(`backend/api/locale/`), der für die Sprache unvollständig
sein kann. Derzeit werden nur deutsche API-Fehler übersetzt;
andere fallen auf Englisch zurück.

### "Wie trage ich eine Übersetzung zurück zum Upstream bei?"

Eröffnen Sie einen Pull Request gegen das RASTATIME-
Repository mit den aktualisierten `.po`-Dateien. Die
kompilierten `.mo`-Dateien werden auch committed —
führen Sie `scripts/compile_messages.py` vor dem Committen
aus. Siehe [`CONTRIBUTING.md`](../../../CONTRIBUTING.md)
für den vollständigen PR-Workflow.

### "Kann ich maschinell übersetzen als Ausgangspunkt?"

Ja — so funktionieren Französisch und Spanisch derzeit.
Führen Sie die .po durch DeepL, Google Translate oder ein
lokales Übersetzungsmodell, markieren Sie jeden maschinell
übersetzten String als `#, fuzzy` und säubern Sie ihn von
Hand. Der fuzzy-Marker sagt gettext, die msgid (Englisch)
zu verwenden, bis die menschliche Überprüfung den Marker
entfernt.

### "Was ist mit RTL-Sprachen (Arabisch, Hebräisch)?"

Die UI wurde von links nach rechts entworfen. Eine
RTL-Sprache hinzuzufügen würde CSS-Überarbeitung zusätzlich
zur Übersetzung erfordern. Derzeit nicht im Umfang;
architektonisch nicht blockiert, nur nicht implementiert.
