## RASTATIME v1.10.0 (2026-11-24)

A feature release on top of 1.9.0: **the import now asks Liquidsoap, the playout engine, whether it
can decode each file**, and a new command checks (and repairs) the files that are already in the
library.

Background: on 2026-11-23 a whole show stayed silent. Liquidsoap refused the scheduled MP3 when it
was queued, although the import check had passed it: Liquidsoap carries its own built-in FFmpeg,
which read that one file as an MPEG program stream, while the standalone ffmpeg used by the import
decoded it without a single message.

It has **no database migration** and **no change to the playout script**: Liquidsoap does not
restart. See *Upgrading* before you install.

### Added

- **Import check with Liquidsoap's own decoder** (analyzer).
  - After the existing FFmpeg check, a short-lived `liquidsoap.exe` asks whether each new file can
    be decoded as PCM stereo. That is the same check that failed on air. It is a separate process,
    not the playout instance: no Stereo Tool, no output, no telnet.
  - The check takes about 0.5 s per import and runs at below-normal priority.
  - When Liquidsoap cannot decode a file, it is remuxed without re-encoding and checked again:
    1. a lossless remux (every stream and every tag, `ffmpeg -map 0 -c copy`);
    2. then the audio only, without the embedded cover picture. In one library file the picture
       caused the same misdetection. The cover shown in the library is kept, because the web
       application stores it at upload.
  - The first remux Liquidsoap decodes goes into the library. `source_md5` keeps the upload's md5,
    so the duplicate check still recognises the original.
  - Only when no remux helps does the import fail, with the reason *"The file could not be played:
    the playout engine (Liquidsoap) cannot decode it, not even after a lossless remux (also tried
    without the embedded picture)"* on the Upload page.
  - Fail-open: when no Liquidsoap binary is found, or Liquidsoap does not answer, the file is
    imported unchecked and the analyzer logs a warning. The check never blocks imports.
  - The binary is the one the `RASTATIME-LIQUIDSOAP` service runs, read from its NSSM entry. After
    a Liquidsoap upgrade, files are checked with the new decoder at once. `RASTATIME_LIQUIDSOAP_EXE`
    overrides it.
- **Library scan `rastatime-api scan_liquidsoap_decode`** (PowerShell in `C:\RASTATIME`).
  - It asks the same probe about every library file, in batches of 200 per process. A full run
    took about 9½ minutes for 25,000 files.
  - The files it cannot decode are written to `logs\liquidsoap-decode-<date>.csv`. Without
    `--repair` nothing is changed.
  - `--repair` (optionally with `--ids 123 456`) remuxes those files in place, with the same two
    variants, but only when Liquidsoap clearly decodes the result:
    - the original is kept in `_replaced\remux-<date>\` inside the storage folder;
    - md5, filesize and `source_md5` are updated;
    - files scheduled within the next 6 hours are skipped.
  - On the live library the first scan found 2 of 25,311 files; both are repaired.
- Manual *Library* (all four languages) describes both.

### Upgrading from 1.9.0

Follow `docs/operator/UPGRADE.md`. In short:

1. Make a backup (*Settings → Backup*).
2. Update the checkout.
3. There is **no migration**, no `composer dump-autoload` is needed and the web application is
   unchanged.
4. Stop **RASTATIME-ANALYZER** first (it locks its executable). Then reinstall the five backend
   packages (`pip install -e`) and restart the services in order (`docs/operator/RESTART_ORDER.md`).
   - The new check is active once the analyzer runs again.
   - The playout script is unchanged, so a PLAYOUT restart does not restart Liquidsoap.
5. Recommended: run `rastatime-api scan_liquidsoap_decode` once and look at the report. Run it
   again after every Liquidsoap upgrade.

### Known limitations

- Windows only.
- `RASTATIME-WORKER` runs from the source tree. It has no wheel among the release files.
- The tempo / key worker (`backend/features`) runs from the source tree in its own environment.
  It has no wheel either.
- The Show Source mount takes one client at a time: while the DJ of the show on air is
  connected, nobody can connect early.
- The schedule under a DJ (trial switch since 1.8.0) covers file rows. A web stream or line-in
  row that falls under a DJ still starts when the DJ ends.
- A file that is remuxed without its embedded picture keeps its library cover, but a later
  *Reset Artwork* finds no picture in the file.
- The playout itself does not yet notice a file Liquidsoap refuses at playout time (for example
  after a Liquidsoap upgrade, before the library scan has run). A check of the next 48 hours in the
  preflight is planned (BACKLOG).
